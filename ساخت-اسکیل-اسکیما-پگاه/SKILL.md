# ساخت اسکیل اسکیما

**ورودی: نام یک اسکیما. خروجی: دو چیز.**

۱. **سند دانش** — `<Schema> Map.md`، همان قالبی که برای `HumanResource` ساخته
   شد: قاعده‌های تفسیر، نقشه‌ی دامنه، دستگاه `cc`، فرهنگ جدول‌ها، فهرست
   اتصال‌ها، تله‌ها.
۲. **اسکیل تسلط** — یک پوشه‌ی کامل کنارِ بقیه‌ی اسکیل‌ها: `SKILL.md`،
   `schema.json`، `scripts/map.py`، چهار `references/`، و `examples/`.

بخش مکانیکی خودکار است. **بخش قضاوتی نه** — و همان است که اسکیل را از یک
فهرستِ جدول به چیزی مفید تبدیل می‌کند.

> **مشکلِ نسخه‌ی اکسلی، اکسل بودنش نبود.** فهرست کاملِ ستون‌ها — چه از
> `run_query` چه از یک فایل — کاملاً کافی است و حتی بهتر: سقف ۵۰۰ سطر ندارد
> و ارجاع‌های بین‌اسکیمایی را حل می‌کند. آنچه `HR Map.xlsx` **نداشت** سه چیز
> دیگر بود: **کلید خارجی، تعداد سطر، و سطر نمونه**. هر سه با سه کوئری ارزان
> به دست می‌آیند و هر سه لازم‌اند تا نقشه از «ادعا» به «دانش» برود. فهرست را
> از هرجا بگیر؛ **این سه را جا نینداز**.

> **قاعده‌ی `ccX` در کلِ دیتابیس `PegahAI` اندازه‌گیری شده** — ۱۰٬۰۳۷ ستون
> `cc` در ۱۸ اسکیما. پس برای هر اسکیمای تازه فرضش کن و از کاربر نپرس.
> [conventions.md](references/conventions.md) زبانِ کامل و سهمِ هر الگو را
> دارد.

> **دو چیز که یک‌چهارمِ کار را عوض می‌کنند.** ۲۵٪ اشیای این دیتابیس **ویو**
> است و `INFORMATION_SCHEMA.COLUMNS` آنها را هم می‌دهد — بدون فیلتر،
> یک‌چهارم نقشه‌ات جدولِ خیالی می‌شود. و ۲۳٪ ارجاع‌های `cc` مقصدشان در
> **اسکیمای دیگری** است — بدون فهرست کاملِ دیتابیس، «حل‌نشده» می‌مانند.

> **اسکیلی که می‌سازی روی دیتابیسِ زنده کار می‌کند، نه روی نقشه.** نقشه
> می‌گوید کدام جدول، کدام مسیر، کدام تله — و برای همین قابل اعتماد است. ولی
> **هر عددی که اسکیل گزارش می‌کند باید از یک کوئری بیاید.** این را در
> `SKILL.md`ِ ساخته‌شده صریح بنویس.

> **نقشه عکسِ یک لحظه است، و این اشکال نیست.** اسکیماها و اشیای هسته ثابت
> می‌مانند؛ حاشیه ممکن است چند جدول جابه‌جا شود. `map.py drift` تطبیق را
> ارزان می‌دهد و **وقتی چیزی عوض نشده ساکت می‌ماند**. جدولی که در نقشه نیست
> ولی در دیتابیس هست، یعنی نقشه قدیمی است — نه اینکه جدول وجود ندارد.

## ترتیب کار

### ۱. اسکیما را قطعی کن

```sql
SELECT s.name AS schema_name, COUNT(t.object_id) AS tedad_jadval
FROM sys.schemas AS s
LEFT JOIN sys.tables AS t ON t.schema_id = s.schema_id
GROUP BY s.name HAVING COUNT(t.object_id) > 0
ORDER BY tedad_jadval DESC;
```

**اسمی که کاربر می‌گوید ممکن است اسکیما نباشد.** و `WHERE name LIKE 'Sales%'`
روی `sys.tables` هیچ‌چیز برنمی‌گرداند، چون `Sales` نامِ اسکیماست نه پیشوندِ
نامِ جدول. همیشه `SCHEMA_NAME(schema_id) = '<Schema>'`.

### ۲. یک آزمونِ سلامت بزن

```sql
WITH params AS (SELECT N'Sales' AS eskima)
SELECT COUNT(*) AS kol_sotoon,
       SUM(CASE WHEN c.COLUMN_NAME LIKE 'cc%' THEN 1 ELSE 0 END) AS cc_dar
FROM INFORMATION_SCHEMA.COLUMNS AS c
CROSS JOIN params AS p
WHERE c.TABLE_SCHEMA = p.eskima;
```

قرارداد `cc` در کلِ دیتابیس برقرار است، پس این کوئری **برای تصمیم‌گیری نیست
— برای اطمینان از این است که به اسکیمای درست وصلی**. یک ثانیه می‌گیرد و
جلوی ساختنِ کل نقشه روی اسمِ غلط را می‌گیرد.

`kol_sotoon = 0` یعنی اسکیما اشتباه است یا خالی — برگرد به گام ۱.

### ۳. درون‌نگری کن → `raw/`

**میان‌بر:** اگر فهرست کاملِ ستون‌های دیتابیس را داری (یک کوئری، خروجی به
فایل — بخش ۰.۰ [introspection.md](references/introspection.md))، مستقیم
بدهش:

```bash
python scripts/build_map.py --inventory inventory.tsv --schema Sales --out schema.json
```

این هم سقف ۵۰۰ سطر را دور می‌زند و هم **۲۳٪ ارجاعی را که مقصدشان در اسکیمای
دیگری است حل می‌کند** — که با درون‌نگریِ تک‌اسکیمایی ممکن نیست.

مسیرِ کامل، وقتی فقط `run_query` داری:

[references/introspection.md](references/introspection.md) — بخش‌های ۱ تا ۶.
پنج فایل: `tables`، `columns`، `pks`، `fks`، و بعداً `dates`.

**سقف ۵۰۰ سطر مهم‌ترین تله‌ی این گام است.** شکل فشرده‌ی ستون‌ها (`STRING_AGG`)
یک سطر به ازای هر جدول می‌دهد و زیر سقف می‌ماند. اگر تعداد سطرِ برگشتی دقیقاً
۵۰۰ شد، بریده شده — تکه‌تکه کن.

### ۴. نقشه را بساز

```bash
python scripts/build_map.py raw/ --schema Sales --out schema.json
```

خروجی دوم `findings.md` است. **بخوانش.** هرچه ماشین نتوانست تصمیم بگیرد
آنجاست.

### ۵. دامنه‌ها را نام‌گذاری کن

`findings.md` خوشه‌های پیشنهادی را می‌دهد. یک `domains.json` بنویس و دوباره
بساز:

```bash
python scripts/build_map.py raw/ --schema Sales --domains domains.json --out schema.json
```

**دامنه از داده درنمی‌آید.** ماشین می‌بیند ۴۰ جدول با `Pardakht` شروع می‌شوند؛
اینکه اسمش «حقوق و دستمزد» است و کجای کسب‌وکار می‌نشیند را تو می‌گذاری.

### ۶. اعتبارسنجی کن — این گام اختیاری نیست

بخش ۹ [introspection.md](references/introspection.md):

- **ارجاعِ یتیم** روی دست‌کم ۱۰ یالِ پرکاربرد. نسبت یتیمِ بالا یعنی یال غلط
  است، نه اینکه داده کثیف است.
- **دانه** روی جدول‌های تراکنشی، قبل از اینکه اسکیل چیزی جمع بزند.
- **دوقلوها**: تعداد سطر و آخرین تاریخِ هر دو.
- **کدهای وضعیت**: توزیع کنارِ دیکشنری.

هر یالی که تست شد `confidence: "CONFIRMED"` می‌گیرد. **یالی که تست نشده حدس
است، هرچقدر هم نامش بخواند.**

### ۷. سند دانش را بساز

```bash
python scripts/scaffold.py readme schema.json --out "Sales Map.md"
```

### ۷.۵ شناسنامه‌ی نسخه را بگذار

```bash
python scripts/build_map.py --inventory inventory.tsv --schema Sales        --snapshot "پشتیبانِ ۱۴۰۵/۰۶" --out schema.json
```

بدون آن، خواننده‌ی نقشه نمی‌داند عکس از کِی است.

### ۸. اسکیل را بساز و پرش کن

```bash
python scripts/scaffold.py skill schema.json --out ../تسلط-فروش-پگاه --name تسلط-فروش-پگاه
```

بعد **همه‌ی `<!-- TODO -->`ها را پیدا کن و پر کن.**
[references/authoring.md](references/authoring.md) می‌گوید هرکدام را چطور.

اسکلت بدونِ این گام **قابل استفاده نیست** — فهرستِ جدول است، نه اسکیل.

## ماشین چه تصمیم می‌گیرد، آدم چه تصمیم می‌گیرد

| ماشین (خودکار و قابل اعتماد) | آدم (بدون این، اسکیل بی‌ارزش است) |
|---|---|
| فهرست جدول و ستون و نوع | نام و مرزِ دامنه‌ها |
| کلید اصلی اعلام‌شده و حدسی | نقشِ هر جدول در یک جمله |
| یال‌های `ccX` و کلیدهای خارجی | اینکه کدامِ دو جدولِ دوقلو مرجع است |
| جدول دوقلوی مشکوک | تفسیر ارجاع‌های بیرونی |
| سطری که پدرش آنی نیست که اسمش می‌گوید | قاعده‌های کسب‌وکاری و واحدِ مبالغ |
| ناسازگاری نوع و عرض | سؤال‌های بازِ «از کارشناس بپرس» |
| ستون‌های مرده و جدول‌های میراث | نمونه‌ی کارِ کامل (`walkthrough`) |
| بازه‌دار / وضعیت‌دار / سطر / دفتر | محرمانگی و شکل گزارش |

**ماشین ساختار می‌دهد، آدم معنا.** اسکیلی که فقط ستون چپ را دارد، همان
`schema.json` است با ظاهرِ مارک‌داون.

## چه چیزی این کار را از یک فهرستِ جدول جدا می‌کند

سه چیز، و همه‌شان در ساختِ `HumanResource` وقت گرفتند:

**تله‌ها.** `build_map.py` خودکار پیدا می‌کند:

- **جدول دوقلو** — `ShiftKari`/`ShiftKary` با نرمال‌سازیِ i↔y و o↔u و
  حذف واکه. اشتباه گرفتنشان **خطا نمی‌دهد، جدولِ خالی می‌دهد**.
- **سطری که زیرِ سربرگِ هم‌نامش نیست** — `DarkhastVamSatr` که زیرِ
  `DarkhastVam` نیست. ماشین می‌بیند ستون `ccDarkhastVam` وجود ندارد و
  کم‌عمومی‌ترین پدرِ ممکن را پیشنهاد می‌دهد.
- **ناسازگاری نوع و عرض** — فرزندِ `int` روی والدِ `bigint`، یا `tinyint` که
  سقفش ۲۵۵ است.
- **ستون مرده** — پسوند `_deeeel` کنارِ ستونِ زنده‌ی هم‌معنی.

**تفکیک شواهد.** هر یال `evidence` و `confidence` دارد:
`DECLARED_FK/CONFIRMED` تا `NAMING_ONLY/LOW`. گزارشی که این تفکیک را نداشته
باشد، حدس را به جای واقعیت می‌فروشد.

**سقف ۵۰۰ سطر.** نقشه‌ای که ستون‌هایش نصفه جمع شده، بی‌صدا غلط است.

## وقتی اسکیما کلید خارجی دارد

آن‌وقت **بخش «کلید خارجی با نام‌گذاری نمی‌خواند»** در `findings.md` پر
می‌شود، و آن گران‌بهاترین خروجیِ کل این کار است: جایی که قرارداد می‌شکند،
دقیقاً جایی است که یک عاملِ بی‌خبر کوئری غلط می‌نویسد و جوابِ به‌ظاهر معقول
می‌گیرد.

این را در `SKILL.md`ِ ساخته‌شده **بالای همه** بگذار.

## وقتی چیزی جواب نمی‌دهد

| نشانه | معنی |
|---|---|
| کوئری اسکیما خالی برگشت | اسم اسکیما غلط است — گام ۱ |
| ستون‌ها دقیقاً ۵۰۰ سطر شد | بریده شده — تکه‌تکه کن |
| `kol_sotoon` صفر | اسکیما اشتباه یا خالی — گام ۱ |
| یال‌ها صفر شد | `cc` هست ولی نامِ جدول‌ها نمی‌خواند؛ نمونه ببین |
| دوقلوهای بی‌معنی زیاد | نرمال‌سازیِ شل خطای مثبت داده — `confidence: low` را نادیده بگیر |

هیچ‌کدام دلیلِ ساختنِ جدول یا رابطه از خودت نیست.
