# رتبه-بندی-مشتریان-پگاه

اسکیل رتبه‌بندی مشتریان پگاه، در فرمت استاندارد `SKILL.md`. مستقل است: این پوشه
را هرجا بگذاری کار می‌کند.

```
SKILL.md                      دستورالعمل — چیزی که مدل هر بار می‌خواند
rules.json                    آستانه‌ها، ضریب‌ها و باندهای رتبه (داده، نه کد)
scripts/rules.py              نمایش و تغییر قاعده‌ها
scripts/rank.py               نمره و رتبه
references/queries.md         کوئری متریک، اعتبارسنجی و کالیبره کردن آستانه
references/metrics.md         کدام جدول، کدام ستون، و جمعیت مشتری از کجا
references/reporting.md       شکل گزارش
examples/sample-input.json    نمونه ورودی کامل
```

## قاعده

سه معیار، هرکدام رتبه‌ی ۱ تا ۵ از روی جدول آستانه‌ها (حد پایینِ هر بازه شامل
است):

| معیار | ضریب | خرده | عمده | زنجیره‌ای | تعاونی ویژه | مشتریان ویژه |
|---|---:|---|---|---|---|---|
| تعداد اقلام خرید | ۳ | ۳۵۰ / ۵۰۰ / ۶۵۰ / ۸۰۰ | ۳۵۰۰ / ۵۰۰۰ / ۶۵۰۰ / ۷۵۰۰ | ۲۰۰۰ / ۳۰۰۰ / ۴۰۰۰ / ۵۰۰۰ | ۳۵۰۰ / ۵۰۰۰ / ۶۵۰۰ / ۸۰۰۰ | ۵۵۰۰ / ۷۰۰۰ / ۸۵۰۰ / ۱۰۰۰۰ |
| درصد ویزیت مثبت | ۴ | ۴۰ / ۵۰ / ۶۰ / ۷۰ ٪ | همان | همان | همان | همان |
| تعداد SKU خریداری شده | ۵ | ۱۶ / ۲۱ / ۲۶ / ۳۱ | همان | همان | همان | همان |

**تعاونی کارکنان (۶۰۷) و «سایر» آستانه ندارند** — شمرده می‌شوند، رتبه
نمی‌گیرند. «سایر» هر `ccNoeMoshtary`ی است که در پنج نوع بالا نباشد (نماینده
۳۵۱/۳۵۲، شبه عمده ۳۵۳، و هر کد تازه). کد «مشتریان ویژه» هنوز تأیید نشده، پس
فعلاً آن مشتریان هم به «سایر» می‌افتند.

```
نمره = (رتبه اقلام × ۳) + (رتبه ویزیت مثبت × ۴) + (رتبه SKU × ۵)   →   ۱۲ تا ۶۰
```

| نمره | رتبه | لنگر | چند تا از ۱۲۵ ترکیب |
|---|---|---|---:|
| ۶۰ | سوپر ممتاز | هر سه رتبه ۵ | ۱ |
| ۴۴ تا ۵۹ | ممتاز | هر سه رتبه ۴ → ۴۸ | ۲۹ |
| ۲۸ تا ۴۳ | درجه ۱ | هر سه رتبه ۳ → ۳۶ | ۶۹ |
| ۱۳ تا ۲۷ | درجه ۲ | هر سه رتبه ۲ → ۲۴ | ۲۵ |
| ۱۲ | درجه ۳ | هر سه رتبه ۱ → ۱۲ | ۱ |

**دو سرِ مقیاس هرکدام یک نمره‌اند** — سوپر ممتاز فقط با ۶۰ و درجه ۳ فقط با ۱۲.
عمدی است: هر پنج لنگر دقیقاً در باند خودش می‌نشیند.

## نگاشت داده

روی دیتابیس `pakhsh` (SQL Server)، همان جدول‌هایی که اسکیل «ارزیابی فروشنده
پگاه» رویشان تست شده:

| معیار | منبع |
|---|---|
| تعداد اقلام خرید | `Sales.AmarForosh_Arshive` — `SUM(Tedad)` با `IsMarjoee = 0` |
| درصد ویزیت مثبت | `Sales.VisitForoshandeh_Arshiv` — `SUM(VisitMosbat)/SUM(MorajehShodeh)` |
| تعداد SKU | `Sales.AmarForosh_Arshive` — `COUNT(DISTINCT ccKalaCode)` |
| نوع مشتری | `ccNoeMoshtary` — ۳۴۷ خرده، ۳۴۸ عمده، ۳۴۹ تعاونی ویژه، ۳۵۰ زنجیره‌ای |
| لاین فروش | `Global.SazmanForosh` |

**کوئری متریک روی `pakhsh` اجرا شده** (سه ماه منتهی به ۲۰۲۶-۰۸-۳۰: ۲۶٬۲۳۵
مشتری)، ولی آستانه‌های شهریور ۱۴۰۵ روی هیچ بازه‌ای اجرا نشده‌اند و زنجیره‌ای و
تعاونی ویژه اولین بار است که رتبه می‌گیرند. برای هر بازه‌ی تازه بخش
«اعتبارسنجی» در `references/queries.md` را انجام بده.

شش تله که وقت زیادی می‌گیرند اگر از قبل ندانی:

- **مشتریِ بی‌خرید در جدول فروش نیست** — اگر جمعیت را از آنجا بگیری، ضعیف‌ترین
  مشتری‌ها اصلاً رتبه نمی‌گیرند و توزیع بهتر از واقعیت درمی‌آید.
- **ویزیتِ نبوده باید `NULL` بماند، نه ۰.** «ویزیت نشده» با «ویزیت شده و نخریده»
  یکی نیست؛ اولی «بدون داده» است و رتبه نمی‌گیرد.
- **کدِ ناشناخته بی‌صدا به «سایر» می‌رود** و رتبه نمی‌گیرد — خطا نمی‌دهد. کوئری
  ۵ تنها جایی است که کدهای واقعیِ بازه را به تفکیک می‌شمارد؛ هر بار بزنش.
- **بازه در برگه نیامده.** پیش‌فرض سه ماه است و اگر عوض شود، همه‌ی رتبه‌ها عوض
  می‌شوند بدون اینکه هیچ عددی غلط به نظر برسد.
- **درصدِ ویزیت از دو ویزیت، درصد نیست** — `min_visits` ستاره‌دارشان می‌کند ولی
  از نمره کم نمی‌کند. بازه‌ی کوتاه این را فراگیر می‌کند.
- **معیارِ اشباع‌شده تمایز نمی‌دهد.** اگر آستانه برای یک نوع مشتری خیلی پایین
  (یا خیلی بالا) باشد، همه یک رتبه می‌گیرند و جدول درست حساب‌شده ولی بی‌معنی
  درمی‌آید. `rank.py` بالای ۸۰٪ هشدار می‌دهد.

## ایمپورت

در بخش Skills، «افزودن از URL» و آدرس این پوشه در گیت‌هاب:

```
https://github.com/<owner>/<repo>/tree/main/رتبه-بندی-مشتریان-پگاه
```

کل پوشه با هم می‌آید. چون اسکریپت اجرایی دارد، اسکیل **خاموش** ایمپورت می‌شود؛
بعد از اینکه یک نفر `scripts/rank.py` را خواند، روشنش کنید. تغییرات این فایل‌ها
تا ایمپورت دوباره به محصول نمی‌رسد.

## اجرای مستقیم

```bash
python scripts/rank.py examples/sample-input.json
python scripts/rank.py examples/sample-input.json --type zanjirei
python scripts/rank.py examples/sample-input.json --summary
python scripts/rank.py - --json < metrics.json
```

پایتون ۳.۹ به بالا، بدون هیچ وابستگی بیرونی.

## تغییر قاعده‌ها

همه‌ی عددها در `rules.json` است — آستانه‌ی هر معیار به تفکیک نوع مشتری، ضریب‌ها،
باندهای رتبه، کدهای نوع مشتری و کف ویزیت. **دستی ویرایشش نکنید**؛ `rules.py`
ورودی را اعتبارسنجی می‌کند، `version` را به تاریخ شمسی امروز جلو می‌برد و جدول
جدید را چاپ می‌کند:

```bash
python scripts/rules.py show
python scripts/rules.py set grades 60 44 28 13
python scripts/rules.py set item_count.omde 3500 5000 6500 7500
python scripts/rules.py set item_count.zanjirei 2000 3000 4000 5000
python scripts/rules.py set weight.sku_count 5
python scripts/rules.py set codes.vizheh 354
python scripts/rules.py set ranked.taavoni_karkonan 1
python scripts/rules.py set min_visits 3
python scripts/rules.py set item_count.omde 18000 26000 34000 42000 --dry-run
```

آستانه‌ی هر معیار چهار عدد صعودی است (حد پایینِ رتبه‌های ۲ تا ۵)؛ باندهای رتبه
چهار عدد نزولی (حد پایینِ سوپر ممتاز تا درجه ۲ — آخرین رتبه کف است و عدد
نمی‌گیرد).

## تصمیم‌هایی که در قاعده‌ها کدگذاری شده

- **حد پایینِ هر بازه شامل است.** جدول برگه هم‌پوشانی دارد (۶۵۰ هم در «۵۰۰ تا
  ۶۵۰» است هم در «۶۵۰ تا ۸۰۰»)؛ اینجا ۶۵۰ رتبه ۴ می‌گیرد و «بیشتر از ۸۰۰»
  یعنی ۸۰۰ به بالا. حفره‌ی جدول SKU (عدد ۱۵) به رتبه ۱ می‌رود.
- **آستانه فقط در `rules.json` است.** کوئری متریکِ خام می‌دهد و رتبه نمی‌سازد؛
  اگر `CASE`ی برای رتبه به SQL اضافه شود، اولین تغییر آستانه دو جواب متفاوت
  می‌سازد که هیچ‌کدام غلط به نظر نمی‌رسند.
- **معیارِ بدون داده رتبه نمی‌گیرد** و آن مشتری نمره‌ی ناقص («۲۴ از ۴۰») دارد و
  ته جدول می‌نشیند. با رتبه ۱ پر نمی‌شود.
- **کف نمره ۱۲ است، نه صفر.** مشتری‌ای که هیچ نخریده هم ۱۲ می‌گیرد؛ «۱۲» یعنی
  کفِ مقیاس، نه هیچ.
- **هر نوع مشتری یک جدول جداست** و هم‌نمره‌ها یک جایگاه می‌گیرند. `rank.py`
  بینشان ترتیب مصنوعی نمی‌سازد.

## آنچه هنوز باید با مدیر فروش پگاه چک شود

- **بازه** — سه ماه پیش‌فرض است، در برگه نیامده. سه ماه انتخاب شده تا معیار
  ویزیت معنا داشته باشد؛ در یک ماه ۷۲٪ خرد زیر کف سه ویزیت می‌افتند.
- **آستانه‌ی «تعداد اقلام»** — عددهای شهریور ۱۴۰۵ از مدیر فروش آمده ولی روی هیچ
  بازه‌ای اجرا نشده‌اند. روی سه ماه منتهی به ۲۰۲۶-۰۸-۳۰ عددهای قبلی اشباع بودند
  (میانه‌ی خرد ۱۴۹ قلم و ۱۴ SKU). کوئری صدک‌ها در `queries.md`.
- **آیا ویزیت و SKU هم باید بین نوع‌ها فرق کنند** — الان برای هر پنج یکی‌اند.
- **«تعداد اقلام»** — `SUM(Tedad)` (واحد کالا) گرفته شده، نه تعداد سطر فاکتور.
- **کد `ccNoeMoshtary` مشتریان ویژه** — آستانه‌اش هست، کدش نه.
- **آستانه‌ی تعاونی کارکنان و «سایر»** — تا نیامده، رتبه نمی‌گیرند.
- **مرجوعی** از اقلام و SKU کم نمی‌شود.

## پیوند با بقیه‌ی اسکیل‌ها

این اسکیل **قاعده‌ی کسب‌وکاری** است. برای هر چیزی بیرونِ سه معیار و هفت
نوع، نقشه‌ی اسکیما هست:

| چه می‌خواهی | اسکیل |
|---|---|
| مسترِ مشتری، اعتبار، مسیر، فاکتور | `تسلط-فروش-پگاه` |
| نوع مشتری (`Goroh` با `ccGorohLink=304`)، تقویم، لاین فروش | `تسلط-مشترک-پگاه` |
| کالا و SKU، بچ | `تسلط-انبار-پگاه` |
| بدهکاری، بستانکاری و وصولِ همین مشتری‌ها | `تسلط-خزانه-پگاه` |
| نمره‌ی فروشنده‌ها | `ارزیابی-فروشنده-پگاه` |

**«نوع مشتری» جدولِ خودش را ندارد** — `ccNoeMoshtary` (۴۸ ارجاع در
خانواده) سطرهای `Global.Goroh` با `ccGorohLink = 304` است. تله‌ی ۲ («کدِ
ناشناخته بی‌صدا به سایر می‌رود») از همان‌جا زاده می‌شود.

**نامِ دیتابیس:** `pakhsh` نامِ اتصال است؛ نقشه‌ها کاتالوگ را `PegahAI`
می‌نامند و نامِ اسکیما و جدول در هر دو یکی است.

نقشه‌ی کامل خانواده، ماتریسِ ارجاع و فهرستِ ارجاع‌های حل‌نشده در
[../SKILLS.md](../SKILLS.md). عددها را `crosslink.py` می‌سازد؛ دستی
به‌روزشان نکن.
